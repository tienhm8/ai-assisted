# Cache Rules

> Status: **Approved** (Tech Lead approved 2026-11-13). Mandatory Rule when a change alters cache keys, values, or eviction timing (load condition in `load-conditions` §1).

1. The database is the source of truth. Clearing the entire cache must not change business results, only make them slower. On a cache miss, read the source; do not treat a miss as "does not exist".
2. Optimize the source first, cache second: the query is already optimized (index, query rewrite, table structure); cache does not replace source optimization. If the source is a DB query, have the post-optimization execution plan; if there is no DB to run it on yet, record it as an assumption and verify before implementing. Then cache only when all six conditions hold: read-heavy; expensive query or computation (complex joins, aggregation, external service calls); reproducible from the source; the business accepts stale data within a defined staleness window; TTL and every invalidating event are defined; data is correctly separated by user, tenant, and permission.
3. Do not cache: balances, financial transactions, payment status; contended inventory or reservation status; business locks; secrets, tokens, passwords, OTPs, and security state; continuously changing data; rarely read data. Exceptions require an approved ADR. The cache's stampede-protection lock must not be used as a business lock.
4. Cache keys must not contain `sensitive` or `secret` data (email, phone number, ID document number); use internal IDs. Personal data (`secret`) may enter the cache only when the design records all of the following and Security approves: key scoped to user or tenant; connection to the cache uses TLS and a per-service account; if the cache persists to disk, encrypt it, or disable persistence for that key group; short TTL; account deletion or deletion at the data subject's request also deletes the cache keys in the same flow; cache only the fields needed.
5. Delete keys only after the transaction commits successfully. After a DB write, delete the key, do not update it; overwrite only with a version comparison and only write when newer. Deletion lives in the data access layer of the module that owns the data; other modules emit events, they do not delete on its behalf.
6. If data depends on tenant, viewer, permission, or language, the key must include that factor. Every key holding data has a TTL with jitter; do not cache error results.
7. A cache that lives longer than one request and is per-instance (L1) must be invalidated on every instance when data changes, and its TTL must not exceed the TTL of the shared cache (L2).
8. Coalesce requests missing the same key so the number of DB queries does not grow with the number of requests; waiting requests have a time limit.
9. A cache failure must not fail the request: bypass the cache, read the source, log it. Cache call timeout is shorter than the source query, retries are bounded; concurrent DB queries are bounded. Do not use server-blocking commands like `KEYS`.
10. Production with a cache has a warm-up job. The job runs on only one instance, loads a selected key set in batches with a DB load limit, shares the load function with the read path, does not overwrite newer data; a failed job does not block startup.
11. Cache lives only in the repository of the module that owns the data, or in the adapter calling an external service; controllers and services do not call the cache. The write path reads data from the DB, not through the cache. Values are read models with only the needed fields, not ORM entities.
